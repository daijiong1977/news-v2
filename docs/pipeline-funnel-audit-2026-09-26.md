### 来源到底怎么轮换

`db_config.load_sources()` 先过滤启用状态和星期，再把 `next_pickup_at` 已到期/为空的来源放在前面。每组按以下键排序：

`is_backup → next_pickup_at → priority → cadence_days → last_used_at`

到期来源不足配额时，会用尚未到期的来源补齐。因而两日/七日 cadence 是轮换偏好，**不是绝对禁止提前读取**；priority=1 也不等于每天必选。来源是否被读取、是否提供可用正文、是否最终发布，是三个不同结果。

成功发布的来源更新 `last_used_at` 和 `next_pickup_at`；选中但未发布的来源另记 probe outcomes，可能调整下次读取时间。这意味着当天反复重跑会改变后续来源排序。

手工指定 `run_date=2026-09-26` 控制编辑日期与历史窗口，但来源轮换和 RSS 年龄仍按执行日期/时间计算；主编 prompt 也使用执行时的 UTC 日期。它不是恢复 9/26 当时的历史 RSS 快照。未来最好统一记录 `edition_date` 与 `fetched_at`，明确各处使用哪个时间。

### Jev 的 10 / 6 / 4 分别是什么

- 最多 **10** 篇保留在 Jev 池。
- 其中最多 **6** 篇标记 `send=true`，交给主编；不是固定把列表前 6 项截走。
- 若达到编辑门槛的文章不足 **4**，可以用较低分稿补到 4，但不会因此越过已判定的同事件等硬条件。
- 送主编的集合一般每 feed 最多 2 篇；质量差距明显时可到 3 篇，极薄来源池为补到 4 还有额外放宽。它不是全流程「每来源最多 2 篇」。保留池的备用条目也不受同一个 2 篇上限约束。
- Fun 的重大游泳/网球新闻在同一次评分中获得额外优先级；普通招募、训练或旧赛事访谈不获得重大赛事加分。没有每天必须发布游泳/网球的硬配额。
- Jev 故障/关闭时可回退到每栏前 10 篇，主编可能直接看到这些条目；上表描述的是本轮实际启用成功的 Jev 路径。

## 8. 备用与降级路径：审计发现的边界

这些是代码路径复核发现的限制；除注明本轮实测外，不表示本轮已发生错误发布。

| 发现 | 影响 | 建议 |
| --- | --- | --- |
| 历史/跨栏同事件判断主要作用于 Jev `chosen`；`rest` 仍可能保留同事件排除项，且未遍历的低排名项不一定做过全部历史检查 | `top-10` 不等于十篇都通过同样去重检查；备用晋升只对当前栏目已选文章再比较，历史或其它栏目约束可能不完整 | 所有正选、备用、deep-dig 在最终入选时使用同一个历史+跨栏事件检查；保留硬性拒绝原因 |
| deep-dig 重新读本轮相同来源的前 15 条 | 不会自动调用未选中来源；并非只读此前没抓过的第 5–15 条，某些早期淘汰稿也可能再次出现；该分支没有重跑完整历史过滤 | 缓存整个已判定候选集合及拒绝原因，再补真正新增候选；统一最后的去重门禁 |
| top-10 中存在适配度不合格项和重复 URL（本轮实测） | 占用备用池名额，实际可用备用数少于表面数量 | 对可发布性硬条件先筛，再按不同事件/题材/出版方组建备用池；保留条件性备用与拒绝项的区别 |
| 题材标签在 Jev 初选之后生成 | 「优先三个题材」只能在已经送进来的有限集合里调换，无法挽回前面被挤出的题材 | 在分栏后的排名调用中顺带返回题材，或提前批量标注；让题材偏好参与最多 6 篇的组成 |
| 最后 `_prefer_final_source_diversity()` 在题材重排之后执行 | 不同来源的排序可能再次增加题材重复，与用户的题材优先目标存在冲突路径 | 统一 final selector：安全/同事件为门槛，题材、出版方、编辑分数按明确优先序一起选 |
| 独立安全审核缺失时，当前代码在重试后仍允许退回改写模型自评分 | 现有实现并非「独立审核缺失必拒绝」；本輪日志为 4+1+4+4，共 13/13 获得独立结果 | 至少单独显示 fallback；若执行「必须独立复核」要求，应将仍缺失的稿留待审核/替换，不用 Jev 代替 |
| pack 为凑齐数量可带入旧稿 | 与“每天 3 篇全新、7 天不重复”的目标不是同一规则 | 报告 `fresh_count`、`carried_count`；单独决定允许少一篇新稿还是展示带日期的旧稿 |

Jev 本身也有故障放行逻辑：分类不确定时保留原栏目，排名失败回到旧截取方式，部分事件配对失败视为未判定重复。因此不能把一次流程成功或 URL 无重复，描述成对全部语义重复的绝对证明。

## 9. 耗时、调用与优先优化位置

流水线主体 371.9 秒；Actions 从创建到完成约 421 秒；网站同步约 10 秒，已包含在 Actions 完成时间附近。

| 阶段 | 本轮耗时 | 说明 |
| --- | ---: | --- |
| 来源抓取 + 早期历史过滤 | 5.5 秒 | 22 个来源尝试，108 条原始记录 |
| Python 禁词 | <0.1 秒 | 5 条删除 |
| Jev 预筛 | 4.1 秒 | 100 条评分，7 条删除 |
| 正文探测 | 9.2 秒 | 93 条输入，77 条保留；可缓存同 URL 避免重复工作 |
| 路由 + Jev 排名 | 9.0 秒 | **已包含路由 3.1 秒**，不要再相加；排名报告自身约 5.7 秒 |
| 题材标签 | 1.5 秒 | 30 条，28 个置信标签，2 个不确定 |
| DeepSeek 主编 | 24.4 秒 | 17 条输入，跨 3 栏一次排序 |
| 正文/图片确认 | 约 0 秒 | 复用 probe 正文，非没有检查 |

阶段加总与主体总耗时有少量差额，包含 checkpoint、数据库更新、备用图片处理等开销。不能把重叠 telemetry 字段直接全部求和。

按栏目单独记录的 enrich 时间：

| News | Science | Fun | 墙钟时间 |
| ---: | ---: | ---: | ---: |
| 74.1 秒 | 87.7 秒 | 91.2 秒 | 165.3 秒，因最多两栏同时执行 |

其它大多数阶段没有保存逐栏目秒数，不以总耗时除以 3 冒充真实统计。若提供者允许三栏同时执行，理论上 enrich 可接近最慢栏的 91 秒，最多约省 74 秒；这是并发估算，不是实测保证。当前代码把 `ENRICH_WORKERS` 限制在 1–2，单改环境变量为 3 不会生效，需要代码改动和限流/重试测试。

Jev 逻辑调用可由本轮计数估算：预筛 100 + 路由 77 + 排名 77 + 题材 30 + 配对 17 ≈ **301 次**。17 次配对已包含历史事件检查的 2 次，不应重复相加。这不是账单 API 请求数：SDK 重试和全部 token 用量没有完整记录。历史事件子集有记录：719 input + 42 output tokens。

Jev 相关墙钟约 4.1+9.0+1.5=14.6 秒，约占主体 4%。因此首要性能瓶颈是 enrich 和正文生成，不是 Jev。Jev 的精确金额需要补齐所有阶段 usage 与实际计费记录后才能给出。

## 10. 推荐试验与验收

**先实施一致性与可观测性，再扩大候选量。** 建议分开 PR，方便回滚和判断哪个变化有效。

| 优先级 | 建议 | 起始参数 / 验收 |
| --- | --- | --- |
| 先做 | 统一备用/深挖/正选的历史与跨栏同事件门禁；明确独立审核 fallback | 用“初选已判重又进入备用”“deep-dig 重遇历史 URL”“另栏已选同事件”样本验证；本轮没有触发 deep-dig，不能用本轮证明该分支正确 |
| 先做 | Science 同轮 URL 去重 + 出版方身份 | 保留原始 feed provenance；不重复抓取、打分；同时报告 feed 和 publisher 数 |
| 接着做 | Science 来源轮换与空源补位 | 来源读取上限先保持 8，正常至多 2 个同出版方 feed；有效出版方少时补 1 个尚未读取来源，设有界尝试预算 |
| 接着做 | 题材提前参与最多 6 篇的组成；最终选择统一权衡 | 首选不同题材，允许同题材不同事件；来源/出版方多样性作为下一层偏好；安全不放宽 |
| 观察 | Fun 保持 10×4，体育来源做小范围加深或专题源试验 | 记录是否看到了重大赛事候选，不能用“发布过一篇游泳”作为重大赛事优先级验证 |
| 后做 | Enrich 并发从 2 试到 3 | 观察限流、失败/重试、耗时及文章附加内容质量；失败可恢复 2 |

先观察 5–7 次正常日运行，不把同一天多次重跑当成独立 A/B 样本。重跑已改变来源轮换，模型输出也有随机性。

每栏都应单独追踪：选中/成功来源数、出版方数、原始/唯一 URL 数、各阶段淘汰原因、送主编数、可用备用数、低于编辑门槛补位数、独立审核覆盖率、实际新稿与带入旧稿数、最终题材/出版方数、各阶段时间和 token。

当前快照给出的起点：News 30 条正文合格、3 个最终出版方；Science 23 条合格记录但仅 20 个唯一 URL、1 个最终出版方；Fun 24 条正文合格、5 条送主编、音乐/游泳/网球三类。若改善了 Science 出版方与备用一致性，同时保持 9 篇新稿和独立审核覆盖率，才算改进；不是只看初始池更大。

### 如何复核下一轮

1. 先记录 Actions run URL、`headSha`、输入编辑日期以及对应 `redesign_runs.id`。
2. 读取该 run 的 telemetry；用 Actions 原始日志取得抓取总数和零结果来源，不能把历史过滤后的 `phase_a_light.counts` 当成原始抓取数。
3. 若读取 `redesign_checkpoints`，使用 `run_date` 与 `stage`；它按日期覆盖，没有 run_id 隔离，`created_at` 可能仍是当天首次插入时间。必须与对应 run 日志/计数核对，后续重跑后无法保证它仍属于要分析的那次运行。
4. 用最终 `redesign_stories`、manifest 与网站 payload 核对实际发布数量、来源及新旧稿。它们也可能随同日重跑更新。
5. 建议后续把逐栏漏斗与来源快照保存到 run-id 对应的不可变 artifact，补齐 `raw → historical_dedup → forbidden → preview → probe → routed → ranked → curator → rewritten → reviewed → published`，避免每次人工重建。

## 12. 用户反馈后实现的两项修复（与上述基线数据分开）

代码与测试在同一 PR 中交付。尚未以这套新规则重新生成 9/26；合并/上线状态应以 PR 和后续 run 为准。

后续反馈又将 Fun 送主编上限从 6 调到 7，并加入早期 Jev 招募识别及各栏目价值评分。详见[栏目价值与送审量](editorial-category-routing.md)。前面的 40→24→5→3 是旧运行的事实，不应改写成新规则已经成功运行的结果；新目标为最多 7 个合格 Fun 候选送主编，最后仍发布 3。

### Science：至少两家合格出版方的目标

- 新增 [editorial_policy.py](../pipeline/editorial_policy.py) 的 `publisher_key`。ScienceDaily 的 feed 合并到一个品牌，已知 BBC/NPR/Smithsonian 域名也有映射；未知来源按 feed hostname 区分。这是显式映射加 hostname 的实现，还没有给来源表添加 `publisher_id` 列。
- Science 的 Jev 每源上限按出版方分组，避免每个 ScienceDaily feed 分别占满额度；News/Fun 保持原有按 feed 配额。
- 主编输入附带出版方，Science 的前三优先达到两家；达到两家的组合中继续优先题材多样性。首批改写因此更有机会包含第二家。
- 独立安全检查后再次选择；若安全稿仍只有一家，按现有编辑门槛尝试第二家出版方的备用稿，仍需正文验证、改写和独立安全流程。
- **这是有合格备选时达成的目标，不以降低安全/编辑标准换数量。** 确实无法凑到两家时明确告警 `Science: only N/2 safe publishers available`。新增 `publisher_counts` 和 `published_counts` 遥测，避免显示 3 个 feed 就误认为 3 家。
- 来源抓取上限暂不变。第 6 节的来源轮换、空源补位、提前 URL 去重仍是后续建议。

### Fun：排除大学招募类报道

- 排除大学招募、verbal commitment、招募班级/排名、签约意向及 transfer portal 类文章；实际大学比赛、冠军、世界/NCAA 纪录仍可参加选择。
- 使用共用的标题/摘要规则，未新增 Jev/DeepSeek 调用。对不明确标题检查摘要开头；明确赛事/纪录标题不因为背景提到曾经的大学招募就被误删。
- 覆盖首轮、Jev 选择与备用池、正文确认、备用晋升、deep-dig、Stage 3 旧 checkpoint，以及打包和旧稿补位。搬栏目也不能成为绕过路径。
- 规则识别仍依赖措辞，不能声称覆盖任何未知表达；后续可用实际漏网例子补测试，或在现有 Jev 判断中加入同等编辑分类。
