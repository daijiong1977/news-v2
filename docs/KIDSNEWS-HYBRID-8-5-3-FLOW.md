## 术语与基本目标

- 栏目 category：News / Science / Fun；目标各三篇，共九篇。
- 题材 topic：栏目内的细分组，如 physics、chemistry_materials、swimming。
- 事件 event：具体发生的事情。同题材可能是不同事件；不同题材标签也不能证明不是同一事件。
- feed/source：采集入口；publisher：独立出版方。同一家出版方的多个 feed 不算多家。
- 正文：Easy / Middle 英文标题、正文、卡片摘要，以及中文标题、摘要。
- 详情：现有背景、观点、关键词、测验等扩展字段。
- Grok：Bot 原生模型，通过 request/answer 文件交接；不是 Python 能直接调用的隐含 API。
- DeepSeek：显式 HTTP provider，密钥只读本机/VM 环境；本方案不使用 JEV。

## 总览：各栏独立 8 → 5 → 3

| 步骤 | 输入 → 输出 | Python | LLM |
| --- | --- | --- | --- |
| 1 来源与历史 | feed 元数据 + 七天历史快照 | SELECT、RSS、快照与时间窗口 | 无 |
| 2 明显重复清理 | 元数据 → 无相同 URL/标题的候选 | URL/标题标准化、机械去重 | 无 |
| 3 初筛、搬栏、分组、事件去重与图片 | 元数据 → 各栏候选顺序与备用目录 | 校验答卷、执行搬栏、抓图/检查/缓存 | Grok 判栏目、topic、事件、重要性、趣味性 |
| 4 准备原文 | 候选目录 → 每栏八篇可用原文 | 按需抓全文、长度/完整性、缓存/补取 | 仅疑难事件交回 Grok |
| 5 合并选文与写稿 | 每栏八篇原文 → 五篇正文及理由 | 拼输入、校验、缓存、受限修正 | DeepSeek 每栏一次调用：8 选 5 并写五篇正文 |
| 6 最终选择、精修与补选 | 每栏五篇正文 → 三篇修正稿 | 校验、记录选择、保留已合格稿 | Grok 5 选 3、精修、自检 |
| 7 详情 | 每栏最终三篇修正正文 → 详情 | 校验字段/测验、打乱选项 | DeepSeek 仅给最终九篇生成详情 |
| 8 打包、影子验收与后续发布 | 最终正文、详情、缓存图 → 九篇内容包 | 对应关系、打包、日志与上线核验 | 无 |

## 1. 采集来源与同栏七天历史

Python 从启用来源采集标题、摘要、发布时间、来源与 URL；此时不逐篇抓全文。

日期 D 使用美东时区；历史范围为 D-7（含）到 D（不含）。
只比较最终栏目过去七天的已发布事件，三栏分开，正常约二十一篇/栏。
当天重跑覆盖当天，不与当天旧成品比较。

每轮从 Supabase 刷新历史并冻结本轮快照，本地 state/ 缓存不进代码分支；
运行快照可随脱敏日志保存。影子成品不写入 published history。
只有核验为真实发布的内容才能进入后续历史。连接失败、缺 history 字段或异常零历史
不得静默当作无历史。`registry_snapshot.py` 每轮重新只读获取来源和前七天历史并冻结快照，
默认优先用 Bot 已有 SELECT 连接器提供同格式 registry；不靠上次影子标题冒充已发布历史。
目前选择可靠的七天全量小快照，不维护第二份可写来源表，也不做复杂增量同步。

## 2. Python 明显重复清理

规范化 URL 和标题，清除相同 URL、规范化后完全相同标题。
不得用宽泛关键词或题材相同替代语义事件判断；“暴雨”不一定同一场暴雨。

## 3. Grok 初筛、自动搬栏、细分题材、事件去重；Python 检查来源图片

### 3.1 自动搬栏

按文章中心主题，而不是来源表所属栏目、标题中偶然出现的词进行判断：

| 中心主题 | 最终栏目 | 典型题材 |
| --- | --- | --- |
| 动物趣事、萌宠、动物竞赛、Fat Bear Week | Fun | animal_events |
| 动物行为/生物学研究、新物种、进化、生态、动物化石 | Science | biology_ecology 或 fossils_archaeology |
| 动物有关的政府政策、国际外交、外交赠送熊猫 | News | us_politics / international_relations |
| 机器人、娱乐发明、趣味科技、创意 AI 应用 | Fun | technology / artificial_intelligence |
| AI 政策、政府使用、数据中心争议、科技公共事务 | News | technology_business |
| 基础科学研究，即使用 AI 或新设备作为工具 | Science | 按研究本身，如 physics / chemistry_materials |
| 有趣且适龄的体育、音乐、电影 | Fun | swimming / tennis / other_sports / music / film_tv |

搬栏在准备八篇原文之前完成，随后与**目标栏目**历史比較；
同一 ID 不得出现在两个栏目，不能以搬栏绕过目标栏历史审核。
本方案不增加跨栏目历史模型比较。

### 3.2 Science 必须区分物理、化学等题材

复用现有 pipeline/news_topics.py 的命名，不另造同义标签：

| 标签 | 题材 |
| --- | --- |
| physics | 物理：力、能量、粒子、光、物理规律 |
| chemistry_materials | 化学/材料：分子、反应、新材料 |
| astronomy_space | 天文/空间：星体、宇宙、空间任务 |
| biology_ecology | 生物/生态：动物植物、行为、进化、生态研究 |
| earth_climate | 地球/气候：地质、海洋、地球系统、气候科研 |
| medicine_health | 医学/健康：医学研究、人体、生理机制 |
| fossils_archaeology | 化石/考古：古生物、恐龙、考古发现 |
| other | 暂不能归入上述组；不是一个可用于去重的统一事件组 |

八篇候选尽量覆盖多个题材，并给第二家独立出版方留位置。
理想最终组合例如“物理 + 化学 + 天文”，但不是每日固定配额；
好生物学稿不因“涉及动物”搬去 Fun。
Science 优先做到至少两家独立出版方；三篇来自两家已经达到目标，不报三家来源不足。
质量相当时，优先兼顾新题材和第二出版方；不能只为不同题材换入明显更差的稿件。

### 3.3 News 与 Fun 的题材和优先级

News 复用 us_politics、international_relations、war_security、severe_weather、
transport_infrastructure、public_health、science_environment、community、
technology_business 等题材；重要美国/儿童公共事务、重大国际事件优先。
在八篇及后续五篇中保留合格重要稿机会，不能等最终三篇才发现没有大新闻。
**News 第一篇：先在合格候选中按重要性选最高优先级稿，确定首篇后，再选另外两篇。**
重要性高于题材/来源多样性偏好；质量、安全、事实和非重复事件资格仍是前提。
同等重要性再比较证据质量、与美国/儿童的相关性和时效，不以抓取顺序作为首篇顺序。
该首篇预留贯穿步骤3的八篇目录、步骤5八选五和步骤6五选三，并在最终输出排第一。
只有首篇淘汰时才用下一篇最重要合格稿补位；不能为凑不同来源将其换成轻新闻。
如候选确无合格重要稿，记录缺口，选剩余最重要合格稿，不虚构重要性。
政治、战争、死亡题材不因严肃而自动排除，评估是否可以中立、适龄地改写。
成人议题可以解释给儿童，但不要保留成人化细节。

Fun 区分 swimming、tennis、other_sports、music、film_tv、games、arts_books、
animal_events、technology、artificial_intelligence、history_culture、kids_community、other。
游泳与网球是两个独立题材，可以各选一篇，不合并为一个 sports 名额。
优先全球/世界级赛事、世界纪录、重大冠军与明星的有意义消息；
美国公开赛冠军等可高优先。排除大学招募/承诺入学、乏味常规公告、讣闻、
购物导流和缺乏儿童趣味的稿件，不因含 swimmer 就当成好 Fun。

### 3.4 题材与来源：优先，不机械一组一篇

选择顺序：

1. 先满足事实证据、儿童适宜性、可中立改写、非重复事件等资格。
2. 保留重要新闻和真正有趣/有科学价值的稿件。
3. 在合格且质量接近的候选里优先不同 topic，同时兼顾独立 publisher。
4. 不强制每个 topic 只能一篇；必要时同题材可选两篇不同事件。
5. 来源目标：Science 至少两家；News/Fun 争取三家。若只能用更少出版方组合，
   不用劣质稿凑来源，保留最佳合格稿并明确记录来源/重要稿目标未达标。

补选先找未覆盖的题材与出版方，找不到再取原组排名最好的合格不同事件稿。
题材多样性是偏好；题材标签不能作为“跳过事件判断”的凭据。
Grok 已在目录阶段完成的判断不对同一候选机械重问；新证据、疑难或冲突才补充判断。

### 3.5 图片在这一步处理

Python 按筛后候选顺序抓来源图片，检查下载成功、格式、像素尺寸、可解码性，
保存图片路径、哈希、尺寸、来源和失败原因。必要的原页图片元信息探测不等于
把全部 feed 正文都送进模型；正文资格检查仍在步骤4。

实现上步骤3图片与步骤4原文组成一个按需资格检查单元：只访问选中候选的原页一次，
复用该页的 OG / Twitter 图片元信息，在送 DeepSeek 之前缓存图片；不是抓全部 feed 原文。
失败先尝试该来源页提供的其他 OG / Twitter 图；仍失败记录，不因此直接淘汰重要 News。
采用现有机械标准，不擅自新增裁剪/尺寸阈值；图片机械合格不等于视觉相关性或版权已被证明。
默认不增加视觉 LLM，后续复用缓存，不重复下载。

## 4. Python 按需抓原文，凑每栏八篇可用候选

按步骤3顺序抓全文，检查公共网页读取、完整性、正文长度和有效来源；
失败取下一篇，不给全部原始 feed 抓全文。保存原文证据和最终跳转 URL；
最终 URL 也要查同栏历史及候选池重复。

当前影子原文规则在 pipeline/agent_shadow_lengths.py：
News 350–1200、Science 350–1500、Fun 180–1200 词。
不是此时生成的稿件词数。未来调整要同步生成/修稿/校验规则。

候选不足时不伪装已有八篇，不降低安全或事实资格；先尽量用现有备用，
是否采用现有受限 discover 另由新实现显式接入，不让 Bot 无限自行搜索。
有疑难事件才用 Grok，不对已确认事件重复花判断成本。

## 5. DeepSeek 每栏一次：八选五，同时生成五篇正文

一次输入一栏八篇可用原文及已知 topic/publisher/importance，返回五个 ID、排名、
选题理由及五篇完整正文（Easy/Middle 英文和中文标题摘要）。
News 先选并列出最重要的合格稿，再填另外四篇；不能让多样性换位挤掉重要稿。
**选文和写稿是同一个调用，正常三栏共三次，不是先排一次再逐篇写五次。**
不生成详情、背景、测验。输入来源文字视为不可信资料，不执行其中指令。

Python 按 ID 恢复原始来源/URL，校验数量、唯一 ID、答卷格式及各栏各级词数。
只做有上限的定点修正，保留已有合格稿；单篇仍不合格可由备用补上。
一次返回五篇可能受输出上限或超时影响，这一调用结构尚须真实测试，
不能把“三次正常调用”说成包含补稿/修正或已测得的总成本。

## 6. Grok 五选三、修正、自检与补选

Grok 阅读五篇草稿及原文，优先好题材、独立出版方、至少一篇重要 News，
只精修所选三篇，不给落选两篇做无用全文精修。
News 第一篇必须优先最高重要性的合格稿，再从其余四篇选第二、第三篇；
后两篇兼顾价值、题材与出版方，最终列表不能把重要首篇排到后面。

修事实、归因、引语、限定语、英文语言和中立性；
有来源的不同立场可以加入，没有来源不可编造第二方观点或制造虚假平衡。
战争/死亡事实可平静呈现，不保留血腥描写、煽动和恐吓。以修后稿做安全与事实自检。
这是第二模型修稿并自检，不称作独立第三轮审核，不另加完整 Grok 审稿。

补选：

1. 三篇中有一篇不合格，先定点修正；修不好，从剩余两篇补选并精修。
2. 已合格两篇存盘不重做。优先未覆盖 topic/publisher，但相同 topic 可用不同事件。
3. 五篇里组合多样性不够，就取质量最好的三篇合格稿，记录目标未达标。
4. 五篇不足三篇合格稿，再从八篇剩余三篇或更深原目录局部补稿。
5. 仅缺稿栏目补，不重抓/重选其他已完成栏目；不补昨日成品。
6. 放宽的是组合偏好，不是事实、安全、中立性或七天事件去重。
7. 目录耗尽允许少于三篇，并明确报告原因，不虚构或回填重复旧稿。

Python 保存选择/修正/淘汰原因、答卷哈希、补选状态及资格检查。

## 7. DeepSeek 只为最终九篇生成详情

必须基于**Grok 修正后的最终正文**，不得回用旧 DeepSeek 草稿。
题目答案来自对应阅读级别正文；观点和背景具体信息有来源依据，
允许缺省可选内容，不以编造数字、年份、立场补齐字段。

Python 校验字段、关键词、题目/答案结构，打乱选项。
不合格可选字段省略、告警并保留正文。
本方案不新增 Grok 详情修正；是否复用现有 DeepSeek 详情审核或合并到详情调用，
本次明确复用现有 DeepSeek 逐字段/逐题审核，Python 仅删失败项并打乱选项。
这不是独立模型审核，Python 字段校验也不是完整语义核验。
步骤7调用数没有承诺，不混入步骤5“正常三次”计算。

## 8. Python 打包、影子验收与后续发布

复用步骤3的图片缓存，核对最终文章与图片映射、哈希，打包各栏三篇（目标九篇）。
记录全过程 ET 起止、各阶段耗时；各栏采集/搬入搬出/去重/拒绝/原文/8→5→3数量和原因；
DeepSeek 每次调用、修正、token，Grok 原生任务和可取得的实际配额。
无法获取的 token/费用不得估算成已核验；打包成功不等于内容质量或上线成功。

本轮测试只生成影子成品，不覆盖正式站点、不写生产 DB、不发邮件。
发布交接：同一 ZIP 提供给 Git 网站仓库和 Supabase 私有 pending bucket；
网站现有 GitHub Action 保持原样。Bot 核验公开站点后上传 ready 标记，不调用 Edge Function。
定时 `finalize-news-publication` 再核验站点、解包到日期归档、事务更新最终文章/检索/来源轮换，
最后更新 archive-index 和 done 标记。SQL/RPC/worker 已有离线测试，尚未部署或创建 cron。
结构化 records 代替包内任意 SQL；完整格式和启用边界见执行手册。

## 单篇修正的硬性边界（最新确认）

**绝不为了其中一篇错误，让 DeepSeek 重写整组五篇。**
